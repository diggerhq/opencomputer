The schema is `computer/schema/computer-api.v1.json`; [API schema](/reference/api-schema) lists its operations, objects, events and errors. The relay, a process on the computer (`SP_WIRE_LISTEN`, default `127.0.0.1:7071`), serves the WebSocket and the workspace file routes. The client is the [opc CLI](/api/cli).

## Transport

| Transport | Operations |
| --- | --- |
| HTTP | Everything, including every write. The only transport for writes, creating and listing sessions, and workspace files |
| [Live](/api/live) (`GET /live`) | New events, deltas and feed rows, pushed. History is read over HTTP |
| WebSocket and HTTP | Reads of one session: `sessions.get`, `turns.get`, `events.list`, `asks.*` and `subagents.*` reads, with the same parameters, result and errors (over the WebSocket, `events.list` takes a `seq` as `after` and returns no cursor) |
| WebSocket only | Terminals |

### WebSocket

Open `/connect` with the subprotocol `opc.v1` (without it: close `4400`). Messages are JSON-RPC 2.0 text frames; binary frames carry terminal data.

The server's first frame:

```json
{"jsonrpc":"2.0","method":"ready","params":{"connectionId":"...","server":{"version":"...","region":null},"protocol":{"features":[]},"limits":{"maxMessageBytes":1048576,"maxRequestsPerSecond":100},"expiresAt":null,"expiresInMs":null}}
```

A request and its response:

```json
{"jsonrpc":"2.0","id":1,"method":"sessions.get","params":{"sessionId":"cs_0123456789abcdef"}}
{"jsonrpc":"2.0","id":1,"result":{"session":{"id":"cs_0123456789abcdef","status":"idle","...":"..."}}}
```

Batches are not supported. Close codes and relay limits: [API schema](/reference/api-schema#websocket-close-codes).

### HTTP

Routes are in the schema's `x-methods` map, for example `POST /sessions/{id}/turns` for `turns.send`. Path parameters replace the id fields of the method's params. `opc` sends them under `/api/managed-agents/computer` of its API URL.

## Authentication

| Layer | Credential |
| --- | --- |
| Hosted service | An API key in the `x-api-key` header, on HTTP requests and the WebSocket upgrade. `opc login` obtains it |
| Relay | `X-Wire-*` headers signed with a key from the host, each signature valid 30 seconds. The relay does not check API keys: whatever fronts it verifies the key and signs the headers |

### Scopes

A credential without a scope list has every scope.

| Scope | Operations |
| --- | --- |
| `sessions:read` | `sessions.get`, `turns.get`, `events.list`, `asks.list`, `asks.get`, `subagents.list`, `subagents.get`, [Live](/api/live), file listing and download |
| `sessions:write` | `turns.send`, `turns.cancel`, `sessions.update`, `sessions.interrupt`, `sessions.compact`, `sessions.suspend`, `sessions.resume`, `subagents.stop`, setting a session aside, file upload |
| `asks:answer` | `asks.answer`, `asks.dismiss` |
| `terminals` | `terminals.open`, `terminals.resize`, `terminals.eof`, `terminals.close` |

The Work routes (`/work/...`) are for the dashboard only for now. No API key can call them: no key is issued with their scopes, and a missing scope list or `*` does not grant them.

A scope may also name sessions (`sessionIds`), be read-only (`readOnly`) and expire (`until`).

| Case | Result |
| --- | --- |
| Scope missing | `forbidden`, `reason: "missing_scope"` |
| Credential expired or revoked | Its connections close with `4001` |
| Caller is not the session's owner and not on its member list | `session_not_found` on every operation. A null member list means the whole organization ([Access](/api/sessions#access)) |
| Terminal opened by someone other than the owner or a listed person (members of an `org` session and admins included) | `forbidden`, `reason: "terminal_owner_only"` |
| Session renamed, archived or otherwise updated, or its access changed, by someone other than its owner | `forbidden`, `reason: "owner_only"` |
| Session set aside by someone other than its owner | `forbidden`, `reason: "aside_owner_only"` |

## Session journal

Every state change in a session is an event with a `seq`, an integer from 1 that increases by one. `Session`, `Turn`, `Ask` and `Subagent` objects are computed from the events. Reads and most writes work on a suspended session.

| Need | How |
| --- | --- |
| Read your own write | A write returns the `seq` of its event. A read with `minSeq` the journal has not reached fails at once with `unavailable` and `retryAfterMs` |
| Resume | Read events `after` the last page's opaque `cursor`, then follow on [Live](/api/live). See [Events](/api/events) |
| Reset (the cursor's position no longer exists: past the end, or the journal was rebuilt) | `409 reset` with `cursor` and maybe `seq`: discard held events above `seq` and read on from `cursor`, or from the start when it is `null` |

## Idempotency keys

Every write takes an `Idempotency-Key` header of 1 to 255 printable characters. A key is scoped to one member and one operation, and kept 24 hours.

| Repeat | Result |
| --- | --- |
| Same key, same parameters | The first result, with its objects re-read at their current state, and `duplicate: true` where the result has that field |
| Same key, different parameters | `409 idempotency_conflict` |
| Same key while the first is in flight | Waits for the first |
| After the first failed | Runs again |

## Errors

Over HTTP an API error is `{"error": {...}}` with the matching status; for a read over the WebSocket it is JSON-RPC error `-32000` whose `data` is the error body.

```json
{"error":{"code":"queue_full","message":"at most 20 turns may wait","status":409,"retryable":true,"retryAfterMs":5000,"requestId":"req_..."}}
```

| Field | Meaning |
| --- | --- |
| `retryable` | True for `rate_limited`, `unavailable`, `computer_unavailable`, `internal` and `queue_full` |
| `retryAfterMs` | How long to wait, when the server knows |
| `field` | The parameter at fault. An unknown parameter is `invalid_request` |

All codes: [API schema](/reference/api-schema#errors).
