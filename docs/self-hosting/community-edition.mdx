<Warning>
This is a preview. It runs the hosted gateway's code on one VM, but its storage is a local emulator, not a production database. Use it to try @computer on your own machine or for a small team, and read [Known limits](#known-limits) before you rely on it.
</Warning>

The single-VM Community Edition (CE) runs all of @computer on one Linux machine you control:

- **The gateway** is the same Worker code as the hosted service (`services/managed-agents`), run under Miniflare in a container. It keeps its state in a Podman volume.
- **The host agent** and every session run on the same VM. Each session gets its own rootless Podman container, as on the hosted service.
- **`/setup`** is a page in the browser where you add the Claude credential, connect the host and optionally connect Slack.

Nothing needs a Cloudflare account, a cloud provider or WorkOS. To serve Slack, you need a public HTTPS URL (see [TLS and a public URL](#tls-and-a-public-url)).

## CE on one VM compared with the other options

| | CE on one VM (this page) | Self-hosted on Cloudflare + cloud VMs | Hosted |
| --- | --- | --- | --- |
| Where it runs | One Linux VM: gateway and sessions together | Workers in your Cloudflare account, plus one Computer VM per organization in Azure, AWS or Google Cloud ([Start here](/self-hosting/overview)) | OpenComputer's infrastructure |
| Gateway storage | Miniflare's local emulation of Durable Objects, D1, R2 and KV, in one volume | Cloudflare's Durable Objects, D1, R2 and KV | Same as Cloudflare |
| Organizations | One | Many | Many |
| Scale | Sessions share one VM's CPU, memory and disk | One VM per organization; Enterprise Edition adds pools | Elastic |
| Sign-in for people | Slack only. The operator uses `SETUP_TOKEN`; SSO is coming soon | WorkOS (dashboard) and Slack | Dashboard and Slack |
| Web dashboard and previews | No | Yes | Yes |
| GitHub App installations | Not yet | Yes | Yes |
| Setup | `.env`, `podman-compose up`, then `/setup` | Wrangler deploys and cloud CLIs | Sign up |

Use CE on one VM to evaluate, or for a small team that wants everything on its own hardware. Use the [Cloudflare deployment](/self-hosting/overview) or the [Enterprise Edition](/self-hosting/enterprise) for anything that has to scale or stay up.

## Requirements

- **OS:** Ubuntu 24.04, x86-64 or arm64. The host installer refuses other systems; Ubuntu 22.04 works only with a Podman of 4.7 or newer from another repository, and that is untested.
- **Podman** 4.7 or newer with `pasta`, and **podman-compose** 1.1 or newer. The host installer sets up both: Ubuntu's podman-compose 1.0.6 ignores compose profiles, so the installer puts 1.6.0 in `/opt/podman-compose`.
- **CPU and memory:** at least 4 vCPUs and 16 GiB for a few concurrent sessions. Add about 1 vCPU and 2–4 GiB for each further session that builds or tests code.
- **Disk:** at least 20 GiB free under `/data` (the session image needs about 10 GiB), and more for every session's workspace. Mount a separate data disk at `/data` before installing, to keep sessions apart from the OS disk.
- **A Claude credential:** an Anthropic API key (`sk-ant-api…`), or a Claude subscription token from `claude setup-token` (`sk-ant-oat…`).
- **Optional:** a domain or tunnel for HTTPS (required for Slack), a Slack workspace where you can create apps.

## 1. Install the host

On the VM, as a user with `sudo`, check out the repository and run the host installer. It installs Node.js, rootless Podman, the host agent's systemd service and the model proxy, and creates the `oc-gateway` user that runs the gateway.

```sh
git clone https://github.com/diggerhq/opencomputer.git
cd opencomputer
sudo selfhost/host-install.sh --dry-run   # checks the machine and prints the plan
sudo selfhost/host-install.sh
```

<Note>
`selfhost/host-install.sh` arrives with the host installer change ([#1204](https://github.com/diggerhq/opencomputer/pull/1204)). Until that change merges, use a checkout of its branch, `feat/selfhost-host-install`, for this step.
</Note>

The host agent does not start yet: it needs the gateway's token, which `/setup` gives you in [step 4](#4-set-up-in-the-browser).

## 2. Configure the gateway

The gateway runs as `oc-gateway`, from that user's copy of the repository:

```sh
sudo -iu oc-gateway
git clone https://github.com/diggerhq/opencomputer.git ~/opencomputer
cd ~/opencomputer/selfhost
cp .env.example .env && chmod 600 .env
```

Edit `.env`:

| Variable | Value |
| --- | --- |
| `SETUP_TOKEN` | Required. The operator's credential for `/setup` and the API. Generate it with `openssl rand -hex 32` and keep it in a password manager. |
| `PUBLIC_URL` | The gateway's public HTTPS origin with no trailing slash, for example `https://computer.example.com`. Leave it empty until you have one; Slack needs it. `SP_ORIGIN` is its older name. |
| `GATEWAY_PORT` | The port on `127.0.0.1` where the gateway listens. Default `8080`. |
| `GATEWAY_ORG` | The one organization's ID. Default `org_selfhost`; do not change it after the first start. |
| `SP_SETUP_OPEN` | `1` keeps `/setup` open after setup is complete. Leave it empty. |
| `CLOUDFLARE_TUNNEL_TOKEN`, `NGROK_*` | Only with a tunnel profile; see [TLS and a public URL](#tls-and-a-public-url). |

You do not need to set `ANTHROPIC_API_KEY`: enter the Claude credential in `/setup`, where it is stored encrypted.

## 3. Start the gateway

To try it in the foreground:

```sh
podman-compose up
```

The first start builds the gateway image, which takes a few minutes. When the gateway is up, `curl -s 127.0.0.1:8080/healthz` answers `{"ok":true,…}`.

To keep it running, use the systemd user unit in `selfhost/systemd/opencomputer-gateway.service`. Podman's `restart: always` on its own does not bring the gateway back after `podman kill` or a reboot. The unit runs a foreground `podman-compose up` and restarts it whenever it exits. As a sudoer, enable lingering for `oc-gateway`, so the unit starts at boot without a login:

```sh
sudo loginctl enable-linger oc-gateway
sudo -iu oc-gateway
install -D -m 0644 ~/opencomputer/selfhost/systemd/opencomputer-gateway.service \
  ~/.config/systemd/user/opencomputer-gateway.service
systemctl --user daemon-reload
systemctl --user enable --now opencomputer-gateway.service
systemctl --user status opencomputer-gateway
```

To use a tunnel profile or another directory, run `systemctl --user edit opencomputer-gateway` and add, for example:

```ini
[Service]
Environment=COMPOSE_PROFILES=cloudflared
WorkingDirectory=%h/elsewhere/selfhost
```

Stop it with `systemctl --user stop opencomputer-gateway`, not `podman stop`; otherwise systemd starts it again.

## 4. Set up in the browser

Open `/setup`: `https://<PUBLIC_URL>/setup`, or over an SSH tunnel before you have a public URL:

```sh
ssh -L 8080:127.0.0.1:8080 you@your-vm   # then open http://localhost:8080/setup
```

Sign in with `SETUP_TOKEN`. The sign-in lasts 12 hours, and changing `SETUP_TOKEN` signs everyone out. Scripts can send `Authorization: Bearer $SETUP_TOKEN` instead.

### Claude credential (required)

Paste an Anthropic API key or a Claude subscription token. It is encrypted in the gateway's storage and sent only to the host's model proxy, never to sessions. The page shows only whether it is set and what kind it is. To change it, paste a new one; **Remove** deletes it.

### Host (required)

The page shows the command that connects the host agent to the gateway, with the token masked. Select **Reveal the command with the token** and run the command on the VM. It writes `/etc/opencomputer/selfhost.env` (mode 0600) with `SP_GATEWAY_URL`, `SP_HOST_ID` and `SP_HOST_TOKEN`, then runs the host installer again, which starts the host agent. The token also sits in the gateway's volume as `host-token`; the gateway never logs it.

When the host connects, the page shows it as **connected**. To finish setup before you connect the host, select **I'll connect the host later**.

### People

For now, the operator signs in to `/setup` with `SETUP_TOKEN`. Once Slack is connected, everyone in the linked workspace can use @computer from Slack, and access to each thread works as on the hosted service.

**Coming soon:** inviting people by email and a member list. Both need sign-in for people, which arrives with SSO.

### When setup locks

Setup is complete once the Claude credential is set and the host is connected or acknowledged. From then on, every `/setup` URL answers 404, so a leaked `SETUP_TOKEN` cannot reconfigure the gateway through the browser. To change something later, set `SP_SETUP_OPEN=1` in `.env`, restart the gateway, make the change, then clear it and restart again.

## Optional: Slack

Slack needs `PUBLIC_URL` set to an HTTPS origin, because Slack only calls HTTPS URLs.

1. In `/setup`, open the **manifest** link: a Slack app manifest with this gateway's event, interactivity and OAuth redirect URLs.
2. At [api.slack.com/apps](https://api.slack.com/apps?new_app=1), choose **Create New App**, then **From a manifest**, and paste it.
3. From the app's **Basic Information**, copy the client ID, client secret and signing secret into `/setup`, then save.
4. Select **Install to Slack** and approve. Slack returns you to a page that says Slack is connected.

Mention the app in a channel, or DM it, to start a session. Saved secrets are shown only as "set"; leave a secret's field empty to keep the stored value.

## Optional: SSO

| Option | Today |
| --- | --- |
| OIDC (issuer, client ID, client secret) | **Stored only; sign-in coming soon.** `/setup` shows the redirect URI to register with your identity provider. |
| WorkOS (client ID, API key) | **Stored only; sign-in coming soon.** |
| SAML | **Not available.** Use your identity provider's OIDC app, or WorkOS, which brokers SAML. |

## Optional: GitHub App

`/setup` stores a GitHub App's ID, slug, private key and webhook secret, but this gateway does not use them yet: GitHub App installations are not wired (see [Known limits](#known-limits)). Until then, sessions use whatever GitHub credentials you give them, for example a token stored as a session secret.

## TLS and a public URL

The gateway listens on `127.0.0.1` only. Put a TLS endpoint in front of it, then set `PUBLIC_URL` to that origin and restart the gateway.

**Caddy reverse proxy**, on a VM with a public IP and a DNS name pointing at it (ports 80 and 443 open). Caddy gets the certificate itself:

```txt /etc/caddy/Caddyfile
computer.example.com {
  reverse_proxy 127.0.0.1:8080
}
```

```sh
sudo apt install -y caddy && sudo systemctl reload caddy
```

**Cloudflare Tunnel**, with no inbound ports. In Cloudflare Zero Trust, create a named tunnel, add a public hostname whose service is `http://gateway:8080`, and put its token in `.env` as `CLOUDFLARE_TUNNEL_TOKEN`. Then start the stack with the profile:

```sh
podman-compose --profile cloudflared up -d
# under systemd: Environment=COMPOSE_PROFILES=cloudflared in the unit's drop-in
```

The `ngrok` profile works the same way, with `NGROK_AUTHTOKEN` and a reserved `NGROK_URL`.

## Run it on a laptop or workstation

- **Linux:** follow the steps above on Ubuntu 24.04. Without a public URL, use `http://localhost:8080/setup` and skip Slack, or run a Cloudflare tunnel.
- **macOS:** Podman runs containers in a Linux VM. Run `brew install podman podman-compose`, then `podman machine init --cpus 4 --memory 8192 --disk-size 100` and `podman machine start`. The gateway runs there with `podman-compose up`, but the host installer needs Ubuntu, so run the host in an Ubuntu VM. Expect it to be slower than native Linux.

To try just the gateway without containers, use `SETUP_TOKEN=$(openssl rand -hex 32) GATEWAY_DATA=/tmp/gw node selfhost/gateway/serve.mjs` from a checkout with `services/managed-agents` dependencies installed.

## Back up and restore

All of the gateway's state is in the `gateway-data` volume: Durable Objects, D1, R2 and KV, the generated keys (`keys.json`), and the host token. Back it up as `oc-gateway`, with the gateway stopped, so the copy is consistent:

```sh
systemctl --user stop opencomputer-gateway
podman volume export opencomputer_gateway-data > gateway-data-$(date +%F).tar
systemctl --user start opencomputer-gateway
```

The archive contains `keys.json`, which decrypts the stored secrets, so store it encrypted.

To restore, stop the gateway, then run `podman volume rm opencomputer_gateway-data`, `podman volume create opencomputer_gateway-data` and `podman volume import opencomputer_gateway-data gateway-data-<date>.tar`, and start the gateway again. Session workspaces live on the host under `/data`, outside the volume. Back them up with your usual disk snapshots.

## Upgrade

```sh
# the gateway, as oc-gateway
cd ~/opencomputer && git pull
cd selfhost && podman-compose build gateway
systemctl --user restart opencomputer-gateway

# the host, as a sudoer, from your checkout
git pull && sudo selfhost/host-install.sh
```

The gateway applies new D1 migrations when it starts. Back up the volume before you upgrade.

## Troubleshooting

| Symptom | Check |
| --- | --- |
| `/setup` answers 404 | Setup is complete and locked. Set `SP_SETUP_OPEN=1` and restart. Or `SETUP_TOKEN` is empty in `.env`. |
| Sign-in loops back to the sign-in page | Without HTTPS, browsers drop the `Secure` cookie when `PUBLIC_URL` is `https://…` but you opened `http://`. Open the `PUBLIC_URL`, or use the SSH tunnel with `PUBLIC_URL` empty. |
| Host shows **not connected** | `systemctl status slack-presence-host` and `journalctl -u slack-presence-host`. `SP_GATEWAY_URL` must use the `GATEWAY_PORT` the gateway listens on, and `SP_HOST_TOKEN` must match the volume's `host-token`. |
| Sessions answer "No model credential is configured" | Set the Claude credential in `/setup` (reopen with `SP_SETUP_OPEN=1`). |
| Slack install says the app is not available | Save all three Slack secrets first. `PUBLIC_URL` must be HTTPS and match the manifest's URLs. |
| The gateway restarts in a loop | `podman logs opencomputer_gateway_1` as `oc-gateway`, and `systemctl --user status opencomputer-gateway`. |
| Gateway gone after `podman kill` or a reboot | Use the systemd unit, with lingering enabled for `oc-gateway`. |

## Known limits

- **Miniflare is not production-grade.** The gateway's Durable Objects, D1, R2 and KV are emulated locally in one volume. Treat it as a single point of failure, and back it up.
- **The production path for self-hosting** runs the actors on a Node.js actor host instead of Miniflare. CE will move to it; the setup flow stays the same.
- **The Account object is a stand-in.** It holds the Claude credential and `/setup`'s settings, but no GitHub App installations, service connections or billing.
- **No web dashboard and no previews.** You configure the gateway in `/setup`, and people use @computer through Slack and the API.
- **People invites and SSO sign-in are coming soon.** Their settings are stored only.
- **One organization per gateway.**

## MicroVM offload (coming)

Today every session runs in a rootless Podman container on the one VM. A coming option will run heavy sessions in microVMs on other machines, so one gateway can serve more concurrent work than one VM holds.
