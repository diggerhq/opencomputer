title: "Deployments and environments"
description: "Understand development, production, immutable deployments, and aliases"

A deployment is an immutable build of one agent. An alias gives a stable name
to the deployment clients should run.

Every project starts with two working environments:

| Environment | Alias | How it changes |
| --- | --- | --- |
| Development | `development` | `npm run deploy -- --watch` publishes source changes |
| Production | `production` | An explicit deploy advances it |

Sessions keep the deployment they started with. Publishing another version
does not change the code underneath an existing session.

## Deploy to production

From the project directory:

```bash
npm run deploy -- --alias production
```

Every deploy first runs `opencomputer doctor`, a local static scan for invalid
connection origins, misplaced tools, and missing secret declarations, and then
prints the project it resolved and the cloud id each local agent deploys as.
Run `opencomputer doctor --json` directly to get structured diagnostics, with
the same resolution under `resolution`, before invoking a deployment agent.

The CLI builds the current source, creates an immutable deployment, and moves
the `production` alias to it. Development remains available for further work.

## Select an agent and environment

Clients identify an agent with `agent-id@alias`:

```text
support@development
support@production
```

The project dashboard's environment selector changes which deployment you are
inspecting. The playground has a separate agent selector when a project
contains more than one agent.

## Review history

Open the project's **Deployments** page to inspect immutable versions, their
aliases, and creation times. Use the deployment ID when correlating a session
with [logs](/agents/logs) or the [debug inspector](/agents/playground).

## Capability manifest

A deployment ID says which build was selected. The capability manifest says
what that build declared, so an application can compare it with what a job
needs before it starts a session.

```bash
opencomputer deployments capabilities <deployment-id> --json
```

```ts
const { manifest, manifestDigest } = await oc.deployments.capabilities(deploymentId);
```

The answer is `{ manifest, manifestDigest }`. The manifest is derived once,
when the deployment is created, from the compiled source and the platform's
own configuration; it is stored with the deployment and never rewritten.
Fetching it again returns the same bytes and the same `manifestDigest`, which
is also returned as the `ETag` header.

```json
{
  "schema": "opencomputer.deployment-capabilities/v1",
  "projectId": "prj_01...",
  "agentId": "support",
  "deploymentId": "support:3f9c...",
  "alias": "development",
  "sourceDigest": "sha256:3f9c...",
  "runtimeImageDigest": "sha256:8a1e...",
  "runtimeImageVersion": "12",
  "runtimeMode": "microvm",
  "models": [{ "provider": "openrouter", "model": "anthropic/claude-sonnet-4.6", "declaredBy": "agent" }],
  "defaultModel": { "provider": "openrouter", "model": "anthropic/claude-sonnet-4.6" },
  "tools": [{ "id": "lookup_customer", "gated": false, "declaredBy": "agent" }],
  "resultSchemas": [{ "toolId": "report", "schema": { "type": "object" } }],
  "skills": [{ "name": "triage", "path": ".opencode/skills/triage" }],
  "mcpServers": [{ "id": "docs", "origin": "https://mcp.example.com" }],
  "subagents": [],
  "connections": [{ "id": "crm", "kind": "http", "policy": { "origin": "https://api.crm.example", "methods": ["GET"] }, "headers": ["authorization"], "secrets": [{ "name": "CRM_TOKEN", "scope": "project" }] }],
  "memory": [{ "id": "requirements", "description": "...", "provider": { "kind": "document", "maxBytes": 8192 } }],
  "regions": [{ "scope": "runtime", "region": "us-east-1" }, { "scope": "workspace", "region": "us-east-1" }],
  "lifecycleCapabilities": { "runtime": "microvm", "persistentSandbox": true, "durableWorkspace": true, "interrupt": true, "terminate": true, "gatedToolApprovals": true },
  "egressCapabilities": { "brokered": true, "connectionOrigins": ["https://api.crm.example"], "mcpServerOrigins": ["https://mcp.example.com"] },
  "createdAt": "2026-09-25T00:00:00.000Z"
}
```

`manifestDigest` is `sha256:` over the canonical JSON of the manifest (keys
sorted, no whitespace). Changing a tool, a result schema, a skill, a model or
a connection policy in the source and deploying again produces a new
deployment with a new digest; deploying unchanged source returns the existing
deployment and its existing digest.

What the manifest contains, and what it deliberately does not:

- **Declarations, not observations.** A model in `models` is what the source
  declared, not the route a session will use; a connection in `connections`
  is its ID, kind and policy, not whether its credential is configured. Both
  are answered by [readiness](#readiness-receipt).
- **No credential material.** Connections list the header *names* they attach
  and the *names* of the secrets they resolve, never values. MCP servers are
  shown by origin, never by full URL. The runtime image is attested by digest,
  never by its internal name.
- **Explicit regions.** `regions` names where the runtime runs and where the
  workspace and artifacts are stored, per scope.
- **Egress is declared, not granted.** `egressCapabilities` lists the origins
  the deployment declared; every request still passes the platform's
  per-request checks.

Every session started on the deployment carries the same digest in its
`session.created` and `agent.rendered` [events](/agents/events), so an event
log can be tied back to exactly the manifest it ran under. If a deployment ID
is redeployed and its manifest changes, every digest it has ever carried stays
retrievable, so a session pinned to an earlier digest can still fetch the
manifest it ran under:

```bash
opencomputer deployments capabilities <deployment-id> --digest sha256:... --json
```

```ts
const pinned = await oc.deployments.capabilities(deploymentId, { digest: event.manifestDigest });
```

An unknown digest answers `404 manifest_not_found`. Deployments created before
manifests existed derive theirs from the deployed artifact on first request;
until that succeeds, both routes answer `503 capabilities_unavailable` with a
`retry-after` header, and sessions started meanwhile carry no
`manifestDigest`.

Declarations are published with the deployment, so a deploy is refused with
`400 invalid_capabilities` when a tool, skill, MCP server or result schema
declaration carries something shaped like a credential (a bearer token, an
API key, a signed URL, a URL with a password). The error names the location
of the declaration (for example `capabilities.resultSchemas[0].schema`),
never its value. A deploy is also refused with `400 invalid_artifact` when
the uploaded artifact has no readable agent metadata: no runtime could start
it, so no manifest is recorded for it.

## Readiness receipt

Some properties can only be observed at a point in time: whether the model
route resolves, whether the platform's storage is writable, whether every
declared connection has its credential in place. The readiness probe checks
them and returns a timestamped receipt.

```bash
opencomputer deployments readiness <deployment-id> --json
```

```ts
const receipt = await oc.deployments.readiness(deploymentId);
if (!receipt.ready) console.log(receipt.checks.filter((check) => check.status === "fail"));
```

```json
{
  "schema": "opencomputer.deployment-readiness/v1",
  "projectId": "prj_01...",
  "agentId": "support",
  "deploymentId": "support:3f9c...",
  "sessionId": null,
  "environment": "development",
  "checkedAt": "2026-09-25T00:05:00.000Z",
  "manifestDigest": "sha256:...",
  "probe": { "mode": "platform", "executesAgentCode": false, "contactsCustomerTargets": false },
  "checks": [
    { "id": "model.route", "status": "pass", "required": true, "summary": "...", "detail": {}, "checkedAt": "...", "durationMs": 4 }
  ],
  "ready": true
}
```

| Check | What passes |
| --- | --- |
| `manifest.integrity` | The stored manifest still hashes to `manifestDigest` |
| `platform.storage` | A bounded write and read-back under an account-owned path of the platform's storage succeeded |
| `artifact.packaged` | The deployed artifact is present, matches `sourceDigest`, and packages exactly what the manifest declares: every tool and whether it is gated, every skill and its path, every MCP server with its origin and connection, every subagent, and every result schema in full. `detail.differences` lists, per section, what the manifest records that the artifact lacks and what the artifact packages that the manifest does not record |
| `model.route` | Every declared model resolves to available access for the environment: a project or agent route, a bound subscription connection of the provider's own kind, or managed access, speaking the protocol sessions would use with it; a binding whose connection cannot serve that provider is `external_unavailable` and fails; a fail-closed route to unavailable access fails. An agent that declares no model is checked against the platform default. `detail.models` names the access of each model |
| `model.catalog` | Every model that routes through managed access exists in the current model catalog; models on external connections are listed in `detail.external` and not checked here |
| `workspace` | The workspace sessions on this deployment would receive is backed by configured storage, on the runtime they would actually start on |
| `connections` | Every declared connection is configured: its secrets exist and are allowed for the connection's origin and every declared redirect origin, its GitHub App installation is active, its provider account is connected for the user running the probe or bound to the agent. Provider grants are per user; when the probe cannot attribute a user, they are reported as `skip` |
| `memory` | Every declared memory resource is configured and selected in this environment with the provider kind and byte limit the manifest records; a resource removed from the environment's selection, or reconfigured since, fails |
| `region` | Each region the manifest declares (`runtime`, `workspace`, `artifacts`) matches the location the platform reports for that scope; `detail.mismatched` and `detail.unknown` name the scopes that do not |
| `lifecycle` | The runtime the deployment needs is configured here |

Each check is `pass`, `fail` or `skip` with its own `checkedAt` and
`durationMs`. `ready` is `true` only when every required check passed: a
required check that failed, or that could not run (`skip`), leaves the
deployment not ready. The response is `200` either way. The CLI exits non-zero on a not-ready receipt after printing
it.

Readiness runs on the platform against the deployment's configuration. It
does not start a session, does not run your agent code, does not send any
model input, and does not contact the targets of your connections or MCP
servers; `probe` says so in the receipt. That also bounds what a `ready`
receipt proves:

- a tool or skill is *packaged*, not that its process started;
- a connection is *configured*, not that its target accepts the credential;
- the model route *resolves*, not that a particular request will be accepted.

Readiness never implies authorization to reach a target. Your application
decides whether a job may proceed by comparing the manifest and receipt with
what the job requires.
